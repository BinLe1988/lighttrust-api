# Token 经济平台通用技术方案

## 1. 产品定位

LightTrust 的新方向不是继续做通用 API 中转，也不是靠 Token 差价盈利，而是改造为面向企业和 AI SaaS 团队的 Token 经济决策平台，服务两条相互增强的业务线：

- Token 经济 SaaS 测算工具：提供离线和在线成本模拟、采购比价、动态路由收益测算、套餐定价建模和压力测试。
- Token 采购咨询平台：支持企业年度 Token 预算测算、厂商组合设计、采购谈判辅助、月度审计和节省金额核验。

首期目标是快速积累企业客户案例，打磨独家 Token 经济测算方法论。因此整体架构应采用“咨询牵引、SaaS 承载、方法论沉淀”的路线：公开测算器负责获客，顾问工作台负责高价值交付，客户门户负责持续复盘，每个项目都反哺行业基准库和方法模板库。

现有 API 转发能力不作为主入口，但可以保留为数据采集、真实账单对账和后续企业审计的基础设施。

## 2. 总体架构

首期建议采用模块化单体，继续沿用现有 Go、React、PostgreSQL、Redis 和系统任务框架，不急于拆微服务。模块边界要清晰，便于未来把 Token 经济计算内核独立为服务。

核心链路如下：

```text
价格与合同数据中心
-> Token 经济计算引擎
-> 场景仿真与压力测试
-> 采购组合优化
-> 咨询项目工作台
-> 报告与客户交付门户
-> 方法论与行业基准库
```

现有 API 中转、钱包、充值、用户额度销售等能力应从主导航中弱化，而不是立即删除。这样既能降低改造风险，也能在需要时导入真实调用数据进行月度审计。

## 3. 可复用的现有能力

LightTrust 当前已有一些非常适合复用的资产：

- 多厂商、多模型、渠道和模型配置体系。
- 输入 Token、输出 Token、缓存、音频和工具调用等细分计费概念。
- `billingexpr` 可配置计费表达式和阶梯结算能力。
- 用户、权限、角色、审计日志和系统任务基础设施。
- Bedrock 对账模块，可比较内部估算、调用日志和云账单。
- React 控制台、报表页面和后台管理交互模式。

这些能力应作为底层基础设施。新的商业价值应集中在独立的 Token 经济领域层，避免把成本公式散落在 Controller、前端组件或原有 relay 逻辑里。

## 4. 核心领域模块

### 4.1 价格目录

价格目录负责维护厂商、模型、区域、币种、公开价格、合同价格、阶梯价格、包量价格、税费、汇率和生效时间。

核心对象包括：

- 厂商：OpenAI、Azure OpenAI、Bedrock、Anthropic、Gemini、国产模型厂商、自建推理服务商等。
- 模型 SKU：模型名称、厂商、区域、模态、上下文长度、能力标签、生命周期状态。
- 计费项：输入 Token、输出 Token、缓存读取、缓存写入、推理 Token、图片、音频、工具调用、批处理、微调、存储等。
- 价格版本：生效时间、价格来源、可信度、公开价或合同价、审计备注。
- 合同条款：承诺消费、最低采购量、折扣阶梯、超额规则、预付包量、有效期、退款或赠送额度处理。
- 汇率与税费假设：币种、汇率、税率、来源、生效时间。

设计原则是永远不覆盖历史价格。任何测算结果都必须绑定具体价格版本和合同版本。

### 4.2 用量预测

用量预测负责把客户的业务假设转化为标准 Token 工作负载。

输入包括：

- 客户、业务线、产品、部门、项目和场景。
- 活跃用户数、人均调用次数、输入长度、输出长度、增长率、峰值倍数、批处理比例。
- 缓存命中率、上下文复用率、工具调用、搜索调用、图片或音频使用。
- 质量等级、延迟等级、合规要求、数据地域要求。

输出是标准工作负载向量，例如月度输入 Token、输出 Token、缓存读取、缓存写入、工具调用次数、峰值请求数和模型能力要求。

用量预测应同时支持手工录入和数据导入。首期优先支持 CSV、云账单导出、LiteLLM 或 OpenAI 兼容日志、LightTrust 内部日志。

### 4.3 Token 经济计算引擎

计算引擎负责在不同厂商和合同条款之间计算可比较的完全成本。

核心公式：

```text
标准工作负载
* 厂商计费规则
* 合同商务条款
* 汇率和税费假设
= 可比较的完全成本
```

引擎输出：

- 按厂商、模型、工作负载、部门、项目和月份拆分的成本。
- 按输入、输出、缓存、推理、工具、批处理和固定承诺消费拆分的成本。
- 有效单价、边际成本、承诺消费使用率和未使用承诺风险。
- 可复算的计算轨迹，用于报告和审计。

实现原则：

- 灵活公式优先复用 `billingexpr`。
- 新增独立领域包承载经济测算逻辑，避免公式分散在接口层。
- 金额、成本和高风险额度转换使用 decimal。
- 每次计算都生成版本化快照。

### 4.4 场景仿真器

场景仿真器负责比较不同业务和技术策略。

首期场景包括：

- 当前采购基准方案。
- 多厂商价格对比。
- 低价模型替换。
- 缓存优化。
- 动态路由节省测算。
- 限流和降级策略。
- 包量或承诺消费采购。
- 活动峰值和用量暴涨。
- 价格上涨、价格下降和汇率波动。

输出包括：

- 总成本、节省金额、毛利率、预算击穿概率和风险等级。
- P50、P90 和极端压力年度成本。
- 敏感性分析，说明哪些变量最影响预算。
- 可解释的推荐理由，用于报告生成。

首期先做确定性场景对比。等积累真实客户数据后，再加入 Monte Carlo 仿真。

### 4.5 采购组合优化

采购组合优化负责在真实约束下推荐厂商和模型组合。

约束包括：

- 最低质量评分。
- 最大延迟。
- 单一供应商集中度上限。
- 数据地域、国产化或合规要求。
- 承诺消费和阶梯折扣。
- 迁移成本。
- 可用性和容量风险。
- 合同到期和续约窗口。

输出包括：

- 推荐厂商和模型组合。
- 基准方案与优化方案成本对比。
- 预期节省金额和下行风险。
- 承诺消费使用率预测。
- 采购谈判抓手。

首期采用规则化、可解释的优化策略。等项目数据足够后，再引入更复杂的数学优化。

### 4.6 套餐定价设计器

套餐定价设计器面向 AI SaaS 公司和小型 API 平台，帮助设计对外售卖的 Token 套餐。

能力包括：

- 按量计费模型。
- 包月套餐。
- 阶梯套餐。
- 免费额度和试用策略。
- 超额计费规则。
- 毛利率和盈亏平衡分析。
- 用量结构和重度用户行为敏感性分析。

输出包括：

- 推荐套餐表。
- 不同客户分层的毛利率。
- 盈亏平衡点。
- 套餐套利和重度用户亏损风险。
- 公平使用限制、模型降级规则等护栏建议。

### 4.7 咨询项目工作台

咨询项目工作台支撑顾问交付，并把每个项目变成结构化方法论资产。

核心流程：

```text
线索
-> 需求访谈
-> 数据收集
-> 基准方案建模
-> 场景设计
-> 推荐方案
-> 报告交付
-> 月度复盘
-> 真实数据校准
```

记录内容包括：

- 客户画像和业务背景。
- 导入的数据文件和字段映射。
- 测算假设和顾问备注。
- 场景版本。
- 人工调整及调整理由。
- 最终推荐方案。
- 客户实际决策。
- 月度真实支出。
- 预测偏差和节省金额核验。

这个模块是咨询业务的操作核心。它既要提升顾问交付效率，也要强制把经验转成结构化数据。

### 4.8 报告与客户门户

客户门户负责把测算结果转成可交付、可复盘、可续费的客户体验。

页面包括：

- 管理层摘要。
- 年度预算预测。
- 厂商成本对比。
- 场景方案对比。
- 采购建议。
- 月度实际成本与预测偏差。
- 节省金额核验。
- 顾问评论和下一步建议。

导出能力包括：

- 面向财务团队的 Excel 工作簿。
- 面向管理层的 PDF 报告。
- 原始计算表 CSV。
- 版本化报告归档。

报告必须包含计算版本、价格版本、合同假设、数据来源、源码与法律声明入口。

### 4.9 方法论与行业基准库

方法论与行业基准库是长期壁垒所在。

沉淀内容包括：

- 行业模板：AI SaaS、企业知识库、客服 Agent、代码助手、小型 API 平台、企业内部效率助手。
- 标准工作负载假设。
- 模型替代矩阵。
- 缓存有效性基准。
- 工具调用开销基准。
- 采购折扣基准。
- 预测误差校准。
- 匿名案例元数据。

每完成一个咨询项目，都应在脱敏和复核后更新基准库。

## 5. 数据与版本模型

系统必须区分可变工作数据和不可变计算证据。

可变数据包括：

- 客户。
- 咨询项目。
- 草稿预测。
- 草稿场景。
- 草稿建议。

不可变数据包括：

- 价格版本。
- 合同版本。
- 预测快照。
- 场景快照。
- 计算结果。
- 报告版本。
- 顾问调整日志。

每份报告都应能从不可变快照复算：

```text
输入快照
+ 价格目录版本
+ 合同版本
+ 方法模板版本
+ 计算引擎版本
+ 顾问调整日志
= 可复现的采购建议
```

这对财务可信度、采购谈判和节省分成核算非常关键。

## 6. 建议的数据表分区

首期数据库可以按以下领域分区：

- `economics_vendors`、`economics_model_skus`、`economics_price_versions`、`economics_price_items`。
- `economics_contracts`、`economics_contract_terms`、`economics_fx_rates`、`economics_tax_rules`。
- `economics_customers`、`economics_engagements`、`economics_data_sources`。
- `economics_forecasts`、`economics_forecast_items`、`economics_forecast_snapshots`。
- `economics_scenarios`、`economics_scenario_snapshots`、`economics_calculation_runs`、`economics_calculation_items`。
- `economics_recommendations`、`economics_reports`、`economics_report_exports`。
- `economics_methodologies`、`economics_benchmarks`、`economics_case_studies`。

所有数据库改动必须兼容 SQLite、MySQL 和 PostgreSQL，遵守现有 LightTrust 的数据库规则。

## 7. API 设计

首期 API 可以按以下资源划分：

- `/api/economics/vendors`
- `/api/economics/prices`
- `/api/economics/contracts`
- `/api/economics/customers`
- `/api/economics/engagements`
- `/api/economics/forecasts`
- `/api/economics/scenarios`
- `/api/economics/calculations`
- `/api/economics/recommendations`
- `/api/economics/reports`
- `/api/economics/benchmarks`

公开测算器 API 和顾问后台 API 应分离。白牌客户只能依赖稳定、文档化的测算接口，不能直接依赖 LightTrust 内部 Controller 行为。

## 8. 前端工作台

主导航建议围绕新业务重排：

- 总览：线索、活跃项目、近期测算、预算风险提醒。
- 价格目录：厂商、模型、价格版本、合同。
- 快速测算：公开计算器风格的成本对比。
- 用量预测：工作负载建模。
- 场景仿真：方案对比和压力测试。
- 套餐设计：AI SaaS 与 API 平台定价模型。
- 咨询项目：顾问交付流程。
- 报告：客户交付物和导出。
- 基准库：方法模板和匿名案例。

界面风格应接近财务、采购和运营工具：信息密度高、可扫描、可审计、便于对比。不要把控制台做成营销落地页。

## 9. 计算原则

Token 经济计算引擎必须遵守以下原则：

- 金额和高风险额度转换使用 decimal。
- 报告生成后，计算输入不可变。
- 同时保存汇总结果和明细轨迹。
- 区分公开价格、合同价格和推算有效价格。
- 区分技术用量假设和商务合同假设。
- 顾问人工调整必须显式记录并可审计。
- 优先使用可解释规则，再考虑黑盒优化。
- 支持从快照确定性复算。

## 10. AGPL 与商业化边界

LightTrust 使用 GNU AGPLv3，并包含额外 NOTICE 要求。修改版必须保留法律声明、可见署名和原项目链接。

本产品线应遵守以下边界：

- 如果修改后的 LightTrust 作为网络服务提供给用户，应为用户提供清晰的对应源码入口。
- 私有化部署、Docker 镜像和安装包应包含 LICENSE、NOTICE、第三方声明、源码提交、构建说明和制品摘要。
- UI 的页脚、关于、法律或署名位置必须保留 New API 署名和原项目链接。
- 商业收入重点放在托管服务、私有化部署、实施交付、咨询项目、节省核验、行业基准数据服务、支持和 SLA。
- 不应把修改后的 AGPL 核心包装为闭源专有产品。
- 如未来确需闭源商业扩展，应采用真正独立的服务边界：独立仓库、独立进程、独立部署、独立数据所有权，并通过稳定 HTTP API 通信。

白牌分发、闭源模块、OEM 授权或商业许可证问题，在客户交付前应交由律师确认。

## 11. 实施阶段

### 阶段一：可销售的咨询 MVP

目标是支撑真实咨询项目并产出专业报告。

范围包括：

- 版本化价格目录，支持公开价和合同价。
- 客户和咨询项目工作台。
- 用量预测录入和 CSV 导入。
- 确定性成本计算引擎。
- 基准方案与替代方案对比。
- Excel 和 PDF 报告导出。
- AGPL 源码入口、署名和交付声明检查。

成功标准：

- 顾问可以完成一次客户成本测算，并且不再把 Excel 当作唯一事实来源。

### 阶段二：差异化 SaaS 工具

目标是让产品价值不依赖纯人工咨询。

范围包括：

- 压力测试和敏感性分析。
- 动态路由节省测算。
- 缓存优化测算。
- 面向 AI SaaS 和 API 平台的套餐定价设计。
- 月度实际账单导入和预测偏差分析。
- 客户门户。

成功标准：

- 客户可以自助完成初步测算，顾问可以把测算结果转成付费项目。

### 阶段三：数据飞轮与白牌能力

目标是把客户案例变成可防御的方法论资产。

范围包括：

- 匿名行业基准库。
- 方法模板版本管理。
- 模型替代矩阵。
- 采购折扣基准。
- 基于真实账单的预测校准。
- 面向小型 API 平台的白牌测算 API。

成功标准：

- 新客户建议能明显受益于历史项目数据，并且系统可以解释基准假设来自哪里。

## 12. 首期交付清单

- 确认第一批目标客户画像和报告模板。
- 定义首批 20 到 50 个模型 SKU 和计费项。
- 定义首批 5 个工作负载模板。
- 实现版本化价格目录和计算快照。
- 建立顾问优先的项目工作流。
- 优先生成 Excel 报告，再做 PDF，因为财务团队会先核对数字。
- 在任何托管或私有化客户部署前，补齐对应源码入口和法律声明。
- 保留 relay 能力，但从主产品路径中降级。

## 13. 待确认决策

- 第一版客户门户采用登录访问，还是采用带权限的报告链接。
- 合同价格按客户存储，还是按咨询项目存储。
- 哪种导出格式作为合同意义上的计算记录。
- 公开测算器是否在展示详细厂商对比前要求登录。
- 当客户拿到建议后自行谈判，节省分成如何核算。
